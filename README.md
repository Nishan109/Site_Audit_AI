# SiteAudit AI

Evidence-based marketing reviews of public websites using Gemini.

## Run locally

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env.local` and configure `GEMINI_API_KEY`. Keep this file private. Existing keys should be retained when updating the app.
3. Run `npm run dev` and open the printed local URL.

Use the npm scripts to start the app. On Windows, the runner adds certificates from the existing Windows trusted-root stores to Node's certificate trust, for Node versions that do not load the system store by default. TLS verification stays enabled. An existing `NODE_EXTRA_CA_CERTS` setting takes precedence. No certificates are downloaded or installed in the operating system.

`GEMINI_MODEL` is optional. The server tries the preferred model, Gemini 3.5 Flash-Lite, Gemini 3.1 Flash-Lite, and Gemini 2.5 Flash (without duplicates). Quota-exhausted or missing models are skipped for that request. Temporary service/network failures are retried at most twice after trying alternatives, with exponential backoff and cancellation support. Each generation has a 75-second total deadline and a 30-second deadline per model attempt, leaving time for a fallback when a model stalls. Authentication, certificate and invalid-request errors stop immediately; reports are never fabricated. Gemini 3 requests use `thinkingLevel` and Gemini 2.5 Flash uses `thinkingBudget`, following the [Gemini thinking guide](https://ai.google.dev/gemini-api/docs/generate-content/thinking). `PAGESPEED_API_KEY` is optional; Google may restrict requests without a dedicated quota.

## How an audit works

Accounts use Supabase Auth and completed reports are saved privately in Supabase. Follow [the account setup guide](docs/supabase-setup.md) to configure the server key, exact auth redirects, email templates, and SMTP delivery. The landing page and local example are public. Live provider actions require a signed-in account. Reopening a saved report uses the recorded evidence without rerunning AI.

The public landing page pairs the website form with an illustrative report showing a finding, its source excerpt and a practical next step. “Explore an example report” opens an entirely local sample with keyboard-accessible Overview, Messaging & copy and Quick wins tabs; it never submits an audit or uses AI quota. Benefits, a three-step workflow and the FAQ explain the actual collection scope and limits. Header and closing review actions focus the same URL form. Report navigation appears after a completed review; its main categories stay visible, while additional checks and creative/research tools are grouped in expandable menus. Address validation retains associated errors and keyboard focus, provider failures preserve the submitted URL, and cancellation aborts the pending request and rejects late results. The waiting screen does not imply that unobserved stages have completed.

- Read the submitted public page plus up to two same-origin about, pricing, features, product or service links. Fetches are fresh and record page URLs, timestamps and real SHA-256 content hashes.
- Page reads have an absolute 30-second budget covering DNS, redirects and the response body. A temporary connection/stream failure, gateway error or stalled first request gets one retry (12 seconds for the first attempt, up to 18 for the second, within the shared budget). Every attempt and redirect revalidates and pins DNS, with TLS verification retained. Access blocks, certificate failures, oversized responses and non-HTML pages are not retried. Cancellation stops collection, and partial response bodies never become evidence. The error screen preserves the submitted URL and offers “Retry this page” after a website timeout.
- Completed React server-streamed HTML is reconstructed from matching boundary/segment markers and literal top-level completion records. Scripts are parsed as data and never executed; genuinely hidden content remains excluded. All specialists use the same completed content, while hashes retain the original response bytes. A collection note identifies reconstructed responses. Empty client-only shells fail before AI research/reviews with an actionable error instead of fabricated copy.
- Ask a research agent for Google URL-context/search evidence. If grounding quota is exhausted, perform real web search through DuckDuckGo (with Bing RSS as a second endpoint), read up to two result pages securely, and ask Gemini to synthesize that collected evidence without using its separately limited grounding tool. Record the actual provider, queries and sources. Only report research as unavailable when no usable researched result can be produced.
- Make separate Gemini requests for Messaging, UX, SEO and Conversion, running at most two specialists at a time, followed by a dedicated AI content-readiness review and SWOT strategy. Each specialist receives the current website evidence. Cancelling or failing the audit aborts any outstanding specialist requests.
- Messaging reads structured headline, body, button, navigation and footer copy, excluding explicitly hidden content and preserving inline text in its sentence. A separate AI review checks each proposed criticism, strength, quick win and rewrite against the surrounding collected copy. Only supported suggestions survive; quick wins must address a retained issue. Rewrites require an exact source excerpt and cited supporting facts, with additional checks against invented numbers and contact details. The messaging score is calculated from four source-cited criteria with published weights; the report shows the reasons, source text, strengths, suggested wording and any sampling limitations. This checks consistency with collected copy, not independent truth of a business's claims.
- The messaging workspace makes criterion scores visible and keeps prioritized findings, original wording, editable suggestions, sources and revision steps together. Users can filter by focus area or available wording options, restore suggestions, and copy/download their current drafts. Edited wording is explicitly unreviewed and does not change the original audit score. Drafts stay mounted while switching report sections and reset for a new audit or page reload. The independent scoring pass does not receive the first reviewer's scores. Responsive display variants are annotated in copy evidence, and static text-concatenation/formatting claims are withheld. Rewrite guards reject unchanged wording and unsupported currency, offer and qualifier claims in addition to invented figures and contact details.
- UX uses structured initial-HTML observations of navigation, headings, link destinations, control names, forms and field associations. Names include native text, label elements, ARIA references and other detectable HTML naming sources. Hidden fields are excluded, disabled/readonly fields do not add editable questions, and a radio group counts as one question. Input values and hidden tokens are not included. An independent review checks each proposed issue and related quick win; unsupported visual/behavior claims are withheld. Four source-backed criteria determine the qualitative HTML score. Unobserved/unassessable criteria are null and excluded from the weighted average, with no fabricated numeric score when everything is unassessed. The UI shows actual observations, strengths, score reasons, sampling limits and which aspects still need browser testing. Rendered mobile layout, color contrast, live link status, keyboard operation and form submission are never represented as completed tests.
- The UX workspace presents a scoped score overview, visible area assessments, strengths and findings ordered by priority. Area filters retain each finding's identity; its improvement plan and readable source observations stay together. Raw observation JSON is available under Technical details. Copy/download exports include all supported findings and browser-testing limits, regardless of the active filter. A deterministic check withholds claims that cited controls are unnamed when their collected names contradict that claim; reports retain the specialist's area instead of guessing it from a title. Source-matched short labels remain valid evidence without padding the quotation.
- SEO collects actual titles, descriptions, resolved HTML/HTTP canonical declarations, crawler-scoped meta and X-Robots-Tag directives, heading outlines, same-origin links and structured-data syntax/type observations. An independent AI pass checks proposed findings and related quick wins, then scores four source-cited areas without seeing earlier scores. Missing structured data is unassessed, not an automatic defect; unknown headers stay unknown. Title/description lengths are informational, and relative canonicals or alternative structured-data formats are not mislabeled as missing. The review cannot establish actual indexing, rankings, link status, rich-result eligibility or Core Web Vitals.
- The search workspace includes a scoped overview, visible score reasons, an illustrative listing built from collected metadata, a page selector, factual signal disclosures, strengths and prioritized fixes with readable evidence. Copy/download plans retain all findings, observations and untested limits regardless of the active filter. Google Search Central references and Search Console access help users follow up on checks that require search-engine data.
- Rejected SEO summary/score explanations receive one bounded reassessment using the same evidence, with no earlier scores supplied. Only rejected fields can change. If reassessment fails or remains unverifiable, affected scores are null and excluded from weighting; the AI summary is withheld explicitly when needed. Verified findings and other assessments remain available. Candidate verification, evidence checks and request cancellation remain enforced. Negated JSON-LD syntax errors and successful parsing are not mistaken for parse failures.
- AI visibility uses a dedicated two-pass content-readiness review. The first pass proposes cited strengths and improvements without scores; the second independently checks each candidate and assesses useful answers (35%), identity/topic context (25%), attribution/supporting detail (25%) and text structure (15%). Exact source IDs resolve to real excerpts or HTML observations; unsupported advice, unknown citations and unverifiable score explanations are withheld. Null criteria are excluded from the weighted score, and no assessed criteria means no numeric score. FAQ/schema quantity never earns an automatic score or penalty. Actual AI mentions, citation likelihood, crawler access, indexing and website claim accuracy remain unmeasured. Guidance: [Google AI features](https://developers.google.com/search/docs/appearance/ai-features) and [OpenAI crawlers](https://developers.openai.com/api/docs/bots).
- The AI visibility workspace includes source-cited assessments, a page selector with actual text excerpts, a separate JSON-LD/microdata/RDFa inventory, prioritized and filterable implementation plans, complete copy/download exports and a live-measurement checklist. Earlier FAQ/schema scores are hidden until a fresh review. Exported plans and print reports preserve source evidence and measurement limits, including when no findings are retained.
- Conversion reviews combine named HTML links/controls, form and field observations, and page copy. A separate AI pass verifies each proposed issue, strength and dependent quick win, then assesses action clarity, decision support, form clarity and next-step expectations without seeing earlier scores. Visitor goals are explicitly hypotheses. Unobserved forms are excluded from scoring, contact links remain valid paths, and published business claims are not independently verified. Guards withhold invented performance lifts, broken-path assertions, visual claims and label criticisms that contradict the collected names.
- The conversion workspace shows source-cited score reasons, selected real action entry points, page-specific form observations, strengths and prioritized implementation steps. It distinguishes these observations from a tested funnel and provides a manual plan for browser checks and measurement. Copy/download exports retain all findings and source observations regardless of the active filter. Actual clicks, submissions, conversion rates and experiment outcomes remain unmeasured.
- A conversion criterion with an unsupported explanation, unknown citation or irrelevant score evidence is explicitly unassessed and excluded from weighting. That optional score field does not discard other verified findings or block the security review. Candidate verification and summary/goal evidence checks remain enforced; unverified claims and synthetic scores are never substituted.
- Quick wins retain their independently reviewed parent finding, typed source evidence and original implementation steps. The shortlist excludes larger-effort work, unlinked suggestions, incomplete benefits, duplicate tasks and promised performance lifts. An incomplete optional benefit is withheld before specialist verification without discarding valid audit findings. Tasks are ordered by estimated effort then finding priority, with at most six tasks and one per finding. Estimates do not measure codebase scope or actual completion time.
- The quick wins workspace offers review-area and manual-status filters, effort/priority ordering, readable observations, related-section navigation and copy/download exports that retain hidden tasks and their statuses. Marking done is reversible and does not confirm a fix or change scores. Progress stays in the open report while switching sections and resets on a new audit or page reload. The print report includes parent findings, steps, evidence and the limits of effort/benefit estimates.
- Validate the model output with runtime schemas. Resolve finding citations against the collected page content. Reject unsupported references rather than displaying a template report.
- Inspect actual response headers and initial HTML for limited security/accessibility observations. Unmeasured items remain unassessed.
- Security reviews use deterministic observations across every collected page: HTTPS URL, HTTP resource references and declared form destinations, CSP header/meta/report-only scope, HSTS max-age, CSP frame-ancestors/X-Frame-Options precedence, nosniff, Referrer-Policy and Set-Cookie attributes. Missing headers remain distinct from uncollected headers. Policy presence is not a vulnerability verdict or a security score. HSTS preload state, browser enforcement, consent and authenticated behavior are untested. Cookie names/values are discarded during collection; resource credentials, queries and fragments are omitted from stored security references. CSP policy strength and full source-list validity require a dedicated review.
- The security workspace offers page and status filters, readable evidence, prioritized configuration reviews, native disclosure controls and complete copy/download plans. Exports and print reports retain all collected pages, hidden tasks, observations and testing limits. Older reports request fresh evidence instead of reusing reassuring “checked” labels. Guidance follows [MDN response-header documentation](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy).
- Reports without a complete security review automatically collect one through `/api/security-checks`, independently of Gemini and the full marketing audit. The section shows collection progress, retryable errors and a manual refresh; previous results remain available during refresh failures. Completed results update the shared report, execution log and print export, with their own collection timestamp. Incomplete responses and mismatched website/report identities cannot replace results. Leaving the section aborts an unfinished request, and late responses cannot overwrite a different report. Scope-only downloads are hidden until real security results are available.
- Accessibility checks inspect each collected page for language, title, headings, image alternatives, field labels, control/link name candidates, label/description references and region declarations. Evidence includes element locations and observed values, with bounded lists and disclosed sampling. Native/ARIA names, hidden referenced labels, image alternatives and native button defaults are considered; placeholder-only fields are flagged for a persistent-label review. Empty decorative alt, multiple H1s, a first H2 and unreferenced duplicate IDs are not automatically treated as conformance failures. Name candidates are a limited HTML heuristic, not a complete Accessible Name computation. Form-field values are not retained in accessibility evidence.
- The accessibility workspace provides page/status/area filters, prioritized steps, source disclosures, complete text/print exports and a practical manual testing checklist. It assigns no WCAG grade; contrast, keyboard/focus behavior, screen-reader output, reflow, target size, dynamic states and alternative quality require browser/assistive-technology testing. Missing or incomplete older results automatically load through `/api/accessibility-checks` without AI quota. Refresh/retry states retain previous evidence on failure, and completed results update the shared report and execution log. Guidance follows [W3C WAI tutorials](https://www.w3.org/WAI/tutorials/) and current WCAG understanding documents.

- PageSpeed insights runs independent, on-demand mobile and desktop tests through Google's PageSpeed API. Lighthouse scores and lab metrics stay separate from CrUX field metrics; field results identify page versus origin scope and retain missing values as unavailable. A Core Web Vitals assessment requires LCP, INP and CLS from the same field dataset. TBT never substitutes for INP, the server-response-time audit never substitutes for field TTFB, and CrUX CLS percentiles are correctly scaled. Modern Lighthouse insights and legacy opportunities preserve provider estimates without promising or adding savings.
- The PageSpeed workspace includes metric explanations, device-specific results, cancellation, retries, and complete text/print exports. Failed refreshes preserve earlier measurements. A Google quota response pauses requests across both devices for the supplied Retry-After delay, or one minute by default. Configure a separate server-only `PAGESPEED_API_KEY` to use your Google Cloud project's quota. During an outage or cooldown, choose **Import Lighthouse JSON** to read a matching Chrome Lighthouse Navigation report in the browser. Imported reports are labeled lab-only and retain their original test time.

- The dashboard recalculates each category from its current source-backed criterion review and equally averages only available category assessments. Invalid, unassessed and legacy scores cannot become zero or inflate the aggregate; security, accessibility and PageSpeed do not contribute a marketing grade. Full category finding lists determine the distinct page/title count and priority breakdown, including AI content-readiness findings, rather than the four-item summary shortlist. Cross-category duplicates keep their highest priority and all review-area links. Incomplete page/evidence records are explicitly excluded from dashboard counts. Linked smaller-effort quick wins are counted separately.
- The overview uses a compact snapshot, a first finding selected from the existing priority order, and a main findings list ahead of the narrower category assessments. Priority, area and local text filters intersect without changing the report totals. Stable finding identities preserve expanded details and filters across report-section navigation; a new audit resets them. Structured observations are displayed when a plain excerpt is absent. One report-header export disclosure offers PDF through the print dialog, complete text download and clipboard copy, independently of screen filters.
- A single Evidence & coverage area retains deduplicated page records, timestamps, collection notes, technical fingerprints, research sources, limitations and execution records. Research retries preserve findings on failure, update shared coverage on success and abort when the report is replaced. Unique source links are not represented as pages read. Section readiness requires complete current-URL security/accessibility results or matching PageSpeed measurements. An empty list does not establish a clean website. PDF and text exports use the same score/count model and do not assign an overall security or WCAG grade.

No hardcoded fallback findings, competitor domains, URL-seeded scores or simulated PageSpeed metrics are used. Repeated issues can legitimately occur across sites; findings should be judged by the cited evidence, not by whether every sentence or score changes.

Existing reports with unavailable research include a **Retry web research** action. A successful retry updates the research summary, sources and execution status while preserving the existing content findings. Public search endpoints may change or throttle requests; the app tries another real endpoint and reports a failure if neither returns usable results. It never treats challenge pages as evidence.

The analysis does not render or interact with audited websites. It cannot establish mobile layout defects, color contrast, real conversion rates, security vulnerabilities, actual AI citations or full WCAG compliance. Only explicitly listed pages were read. Dynamic or protected pages may be inaccessible and return an honest error.

The ad studio has a campaign brief, editable Google/Meta variants, and placement previews for Search, Feed, Stories and Reels. Uploaded artwork stays in browser memory; preview frames preserve their ratios with explicit whole-image or crop controls. Mismatched artwork is identified. Edits remove the original copy score from the active draft, and downloaded text uses the edited copy. Drafts and images stay mounted when moving between report sections, and reset on a new audit or page reload.

Ad generation uses freshly collected business content. Creative comparison requires two valid PNG, JPEG or WebP images under 5 MB each and uses real multimodal assessments. Images are uploaded once and retained across artwork/feed/story/reel preview changes and report navigation. Fit/crop controls affect only illustrative previews; the AI reviews the original images plus supplied copy, focus and optional audience context. Editing review inputs aborts pending requests and marks existing advice stale, preventing stale exports. The review can be copied or downloaded as text. Copy/creative scores are qualitative AI assessments. CTR and conversion performance are not fabricated. Competitor cards require live research. PageSpeed results distinguish Google measurements from imported Lighthouse lab runs. INP stays unavailable when field measurements are missing.

Creative comparison reviews each image in a separate request without its A/B slot label. Both requests use the same rubric and model settings; fallback retries the pair together. The server calculates weighted scores for message, hierarchy, readability and call to action using the selected review focus, then derives the preference from those scores. A difference of three points or less produces a tie, a product rule for avoiding forced preferences between close qualitative scores. Identical image bytes and equivalent supplied copy share one genuine assessment and tie exactly; different copy is assessed separately. Criterion scores and observed evidence are available in each score breakdown and the text export. AI scores can vary between runs and are not calibrated advertising performance metrics.

## Verification

- `npm test`: URL validation, site-specific evidence, unsupported findings, provider failures, JSON/schema validation, image validation, metric identity, comparison order/label mapping, ties, isolated assessments and paired fallback regressions.
- `npm run lint`: lint checks (existing font/image optimization warnings may remain).
- `npm run build`: production compilation and TypeScript checks.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-live.mts https://example.org`: optional real-provider smoke test. This uses configured Gemini quota and writes results to ignored `.next/verification/`.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-messaging.mts https://example.org`: optional focused messaging check using freshly collected page copy and the real configured AI provider. It records the source-backed review in ignored `.next/verification/`.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-ux.mts https://example.org`: optional focused UX check using freshly collected HTML observations and the real AI provider, recording assessed/unassessed criteria and verified findings in ignored `.next/verification/`.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-seo.mts https://example.org`: optional focused SEO check using fresh HTML and response headers with the real AI provider. Source observations, supported findings, assessed/unassessed criteria and verification counts are recorded in ignored `.next/verification/`.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-ai-visibility.mts https://example.org`: optional focused AI content-readiness check using fresh page evidence and the real provider. Saves cited assessments, observations, retained findings and limitations to ignored `.next/verification/`.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-security.mts https://example.org`: optional read-only security-signal check using fresh response headers and HTML without AI quota. Saves the page-specific review and limitations to ignored `.next/verification/`.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-accessibility.mts https://example.org`: optional read-only accessibility-signal check using fresh HTML without AI quota. Saves page-specific observations, evidence, review steps and manual testing limits to ignored `.next/verification/`.
- `node scripts/run-with-ca.mjs --import tsx scripts/verify-conversion.mts https://example.org`: optional focused conversion clarity review of fresh HTML observations and copy using the real AI provider, recording the inferred goal, sources, verified findings and unassessed criteria in ignored `.next/verification/`.

Deployment plans must support the configured route durations. The main audit allows 180 seconds, with shorter deadlines for individual provider and page requests. No deployment or account/billing changes are performed by the app's local setup.
